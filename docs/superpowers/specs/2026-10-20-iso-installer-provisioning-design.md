# Fast, Unattended VM Provisioning — Design

**Spec this argues from:** GitHub issue #2 (https://github.com/CtrlCarlitos/lab-vm-manager/issues/2), reprioritized per the conversation below. The full issue text (Parts A-D, acceptance criteria, out-of-scope list) was read and is incorporated by reference throughout this document — "Part A"/"Part B" citations below point at that real text, not a guess at it. The issue text itself says "deliver interactive installation first... without making a universal unattended installer a prerequisite." This design deliberately inverts that ordering, with Carlos's explicit sign-off (see "Decided, as decided" below).

## Intent and why

Carlos's actual workflow is fast, repeated dotfiles experimentation: spin up a fresh VM, get it to a state where he can log in and copy his `.ssh` keys and `chezmoi.toml` onto it, run his dotfiles, use the box, discard it, and do it again — "almost like containers: spin, run, use, discard." He already has Hyper-V checkpoints for reverting existing VMs; what's missing is a fast, reliable way to go from "pick an ISO" to "a freshly-installed VM with my account already on it and reachable," with zero manual installer babysitting, every single time — not a one-time golden-image step.

Issue #2's own Part D (unattended Windows/Ubuntu installation) was originally scoped as a *bounded research deliverable* — document the approach, don't commit to building it, since the issue assumed interactive installation (Part C) was the primary near-term need. That assumption doesn't hold for Carlos's actual use. The unattended path is the thing that has to actually work; the manual `vmconnect`-and-click-through flow matters far less to him day to day.

This also connects directly to the just-shipped issue #3: once a VM lands with a known username/password, Linux VMs are immediately reachable over SSH (InteractivePassword mode, already built) and Windows VMs over PowerShell Direct (already built, no networking required) — Carlos's "copy in my keys and chezmoi.toml" step is exactly issue #3's file-transfer engine, not new work.

## Goals

- Browse/select an ISO from the existing `E:\ISO` library (issue #2 Part A), read-only, same as originally specified.
- Create a Generation 2 VM (Windows 11 or Ubuntu Desktop) with the correct Secure Boot template and, for Windows, a local key-protector + vTPM — all empirically proven to work on this host already (see "Already proven" below).
- Feed the installer an unattended answer file (Autounattend.xml for Windows; Ubuntu's Subiquity `autoinstall` for Linux) carrying a username and password, with zero manual interaction required once the VM starts.
- Username/password: typed interactively through the normal menu flow (matching the project's existing credential-prompt conventions), or passed as parameters for a non-interactive/scripted caller — including an AI agent driving the tool — which owns remembering what it chose. The tool never persists or echoes the password back.
- Land the VM in a state where issue #3's existing file-transfer tooling can reach it immediately: SSH + password auth enabled for Linux (via the autoinstall config), nothing extra needed for Windows (PowerShell Direct just needs the local account).
- Never modify, rename, or touch the source ISOs in `E:\ISO` — every generated artifact (answer files, seed media, any rebuilt boot media) lives in a separate, controlled workspace.

## Non-goals (for this phase)

- The manual interactive installer launch/finish flow (issue #2 Part C: `vmconnect` wiring, "press any key" UX handling, eject-media-and-fix-boot-order after a manual install) is **not** part of this phase's primary deliverable. It's still a real, wanted feature — proven feasible in live testing already — but it's smaller and lower-priority than the unattended path, and may become its own later plan.
- A universal answer-file system covering every Windows/Ubuntu edition and every possible setting. Scope the first version to what Carlos actually needs (a local account with a chosen username/password, English/US-ish defaults, EULA/license acceptance as required by the OS itself) and document what's out of scope rather than guessing at completeness.
- Checkpoint/snapshot management — Carlos already has that; it's out of scope here.
- Dotfiles provisioning itself (chezmoi, etc.) — issue #2's own text already excludes this, and it's not changed by this reprioritization.

## Anti-goals

- Silently accepting a license/EULA/consent screen that genuinely requires the operator's choice, beyond what the OS vendor's own answer-file schema defines as a settable field (e.g., Windows Setup's EULA acceptance via the answer file is a documented, standard field — that's fine; inventing a way to bypass something the schema doesn't expose is not).
- A VM that silently "looks done" (Running state) when the unattended install actually failed or is still mid-install. Distinct, honest outcomes matter here exactly as issue #2's own acceptance criteria already say.
- Modifying anything in `E:\ISO`, ever, under any circumstance, including the Windows boot-loader-swap technique below (see constraints).

## Constraints

- Everything issue #2 already states as a constraint still applies except the Part C/D ordering: read-only ISO library, preserve existing lock/audit/confirmation/`-ReadOnly` guarantees, Generation 2 Windows 11 + Ubuntu targets only, require VM Off for media/firmware changes, never rotate an existing key protector or disable TPM silently, never commit credentials to audit output.
- No new external tool dependencies beyond what Windows already ships, matching this project's standing architecture (a single, self-contained PowerShell 5.1 script). This was tested directly: Terraform (including its newer Hyper-V providers) was investigated and rejected for this reason — it adds a binary + provider dependency and doesn't solve the actual hard problem (authoring the answer-file content) any better than doing it natively. See "already proven" below for what *is* natively available.
- Credentials: never logged, never written to an audit record, never persisted by the tool beyond the lifetime of the operation that needs them.

## Already proven (live, on this host, this conversation)

Before committing to this design, the core mechanics were tested for real, not just read about:

- `New-VM -Generation 2` + `Add-VMDvdDrive` + `Set-VMFirmware -SecureBootTemplate MicrosoftUEFICertificateAuthority` → booted a real Ubuntu 26.04.1 ISO to the actual installer screen.
- `Set-VMKeyProtector -NewLocalKeyProtector` + `Enable-VMTPM` + `Set-VMFirmware -SecureBootTemplate MicrosoftWindows` → booted a real Windows 11 (build 26300) ISO to actual Windows Setup.
- Both required this session to be elevated (Hyper-V Administrators membership or admin); that's a real precondition the implementation needs to check for and report clearly, not assume.
- The Ubuntu boot reached the installer on the first attempt, no "press any key" issue. The Windows boot hit the known "press any key to boot from CD or DVD" race on the first attempt (firmware fell through to PXE before a keystroke registered) and succeeded on a `Stop-VM`/`Start-VM` retry with an immediate click-then-keypress. This is a documented, real Hyper-V Gen2 quirk (even HashiCorp's Packer tooling hit it: "Gen2 VM boots too fast for boot_command to trigger"), not a one-off fluke.
- A plain, non-bootable data ISO (exactly what both an Autounattend-carrying disk and a cloud-init NoCloud seed volume need) can be built with zero external dependencies via the `IMAPI2FS.MsftFileSystemImage` COM object, which ships with Windows. Confirmed this doesn't need the Windows ADK — the ADK is only needed for *bootable* media.

## Decided, as decided (round 2 — after the builder check)

- **Auto-save SSH connection settings once the unattended Linux install finishes.** Confirmed: the provisioning flow discovers the guest's address and calls the equivalent of `Set-LabSshConnectionSettings` automatically, so the VM is actually reachable by issue #3's file-transfer tooling the moment provisioning reports done — no separate manual `C` step required every time. This is a deliberate, explicit exception to this tool's usual "settings writes are always a manual, confirmed operator action" convention, justified specifically by the "zero manual interaction, every single time" framing this whole phase exists to serve. (Trusting an unknown host's key via menu `K` remains a separate, unavoidable, manual, typed-confirmation step — that one isn't this design's to automate away; it's a deliberate security gate from issue #3.)
- **"Create and provision" is a new, separate action, not an extension of the existing `N` (Create VM) wizard.** `N` stays what it is today — a generic, OS-agnostic blank Gen2 VM creator, still useful on its own. The new flow is its own menu entry (and CLI surface) that creates the VM *and* drives it through the unattended install in one pass, reusing `N`'s existing VM-creation code where it genuinely overlaps rather than duplicating it outright — exact factoring is the builder's call.

## Decided, as decided (round 1)

- **Priority inversion confirmed by Carlos**: unattended install delivery (originally Part D) is the primary deliverable for this phase; the manual interactive launcher (Part C) is explicitly deprioritized.
- **Both OSes wanted**: Windows 11 and Ubuntu Desktop, both for this fast spin/use/discard loop.
- **Ubuntu Desktop, not Server**: Carlos wants the actual desktop experience his dotfiles target. Confirmed via research that this doesn't cost anything technically — Ubuntu 24.04 LTS onward unified the installer, so `autoinstall` is officially supported in the Desktop graphical installer, not just Server (Carlos offered to add a Server ISO too; not needed on current evidence, but there's no harm in having one as a fallback if the Desktop path ever proves unreliable in practice).
- **Credentials UX**: typed interactively in the normal flow; parameterized for a non-interactive/scripted/AI-driven caller, which owns remembering the value. No tool-side persistence or default profile.
- **The "press any key" fix**: rebuild the Windows ISO's boot loader to the no-prompt EFI variant, rather than scripting a keystroke into the `vmconnect` console. Carlos chose this explicitly over the (also-viable, lower-dependency-risk) alternative of using .NET `SendKeys` against the focused console window.
  - Known procedure (Microsoft's own Hyper-V team, documented 2013, mechanism likely still applicable but **not yet verified against the actual ISOs in `E:\ISO`**): inside the ISO, under `\efi\microsoft\boot\`, there are two boot-loader variants — `cdboot.efi` (prompts) and `cdboot_noprompt.efi` (silent) — and similarly `efisys.bin` (prompts) and `efisys_prompt.bin`. Swapping the default files for their no-prompt counterparts and rebuilding the bootable ISO removes the prompt entirely.
  - **Open question for the builder**: the traditional recipe rebuilds the ISO with `oscdimg.exe` from the Windows ADK — an external dependency this project has otherwise avoided everywhere. A more promising, ADK-free alternative (not yet verified) is to extract the original ISO's files, do the same swap, and rebuild the bootable ISO using the already-proven-available `IMAPI2FS` COM object by feeding it the swapped `efisys.bin` directly as its El Torito boot image. Investigate this first; only fall back to requiring the ADK (checked for and failing clearly if absent, matching this project's SSH-tooling-check precedent) if the native approach doesn't pan out.
  - One community report noted the classic file-swap didn't suppress the prompt on Windows Server 2022 — this needs to be verified live against the real ISOs in the library (`Win11_25H2_English_x64.iso`, `Windows11_Client_x64_en-us_26300_9457.iso`) before being trusted as the plan's binding mechanism.
  - The rebuilt ISO is always a new, separate file in a generated-artifacts workspace. The source file in `E:\ISO` is only ever read.
  - Ubuntu does not need this fix — its GRUB-based boot path didn't show the same prompt in testing. Don't build the rebuild logic generically for "any ISO"; scope it to the Windows-specific boot loader layout.
- **Post-install reboot and firmware boot order (settled here, builder's call confirmed, not Carlos's to weigh in on — this is pure mechanics in service of the goal he already stated).** Hyper-V's `Set-VMFirmware -FirstBootDevice` is a persistent, hypervisor-level setting checked on *every* boot, not just the first — it is not "boot DVD once, then prefer disk." Both Windows Setup and Ubuntu's installer reboot one or more times mid-install, and with the DVD still first in boot order, a naive implementation would re-enter the installer (or the no-prompt loader) on every subsequent boot instead of ever reaching the installed OS — a real, previously-documented Hyper-V Gen2 gotcha, not hypothetical. The implementation must detect the installer's first reboot/shutdown (polling VM state is the straightforward mechanism already used elsewhere in this codebase) and, before the VM starts again, either swap the firmware boot order to the disk first or detach/eject the DVD outright — verified live, the same discipline used throughout this project, before being trusted as the plan's binding mechanism. This applies to the unattended path specifically, independent of whatever Part C's (deprioritized) manual "finish installation" step eventually does.

## What's left to the builder

- The exact Autounattend.xml schema fields needed for: computer name, local account + password, skipping OOBE where the answer-file schema allows it, and whichever EULA/license fields the schema exposes as settable (vs. ones that aren't, which stay a real operator decision).
- The exact Ubuntu `autoinstall` YAML fields for: username/password (hashed, not plaintext, per cloud-init convention), hostname, and the `ssh` section enabling `openssh-server` + password authentication so issue #3's tooling can reach the box immediately.
- How the seed media (autoinstall) and the Windows answer-file media are each actually delivered to their respective installers — verify this isn't just "a file that happens to be near the ISO" but something the installer actually consumes (the issue's own words). This needs live verification on a disposable VM, the same discipline this project has used throughout.
- How the tool detects "unattended install actually finished and the VM is reachable" vs. "still installing" vs. "failed" — likely polling for PowerShell Direct/SSH reachability with a sane timeout, not just VM Running state (issue #2's own acceptance criteria already say Running ≠ done).
- Whether to still deliver any slice of Part A/B (ISO browse + VM/media/boot/security prep) as a standalone first plan before the unattended-install plan, given B's VM-creation/media-attach mechanics are shared by both the unattended and (future, deprioritized) interactive paths. This is a sequencing call for `writing-plans`, not fixed here.
- Exact generated-artifact workspace location and cleanup lifecycle for rebuilt ISOs, answer files, and seed media (never `E:\ISO` itself). **One piece of this is settled here, not left open:** the Windows answer-file media carries the local account password in recoverable (base64, not hashed) form for as long as it exists on disk, and the installer reads it across multiple reboots — so its deletion is coupled to "install actually finished," not generic eventual housekeeping. The builder's detection step (above, "how the tool detects unattended install actually finished") and the deletion of the credential-bearing seed media are the same moment, not two independently-scheduled cleanup tasks.
