# Linux Unattended Install — Design

## Intent and why

Issue #2 (ISO discovery, media prep, installer launch) was split into three sequential plans. Plan 1 (Foundation) and Plan 2 (Windows unattended install) are both merged and live-proven on this host. This is Plan 3: the same "create and provision" idea, for Ubuntu Desktop — a single new menu action takes a freshly created, boot-profiled VM all the way to a logged-in Ubuntu desktop with a known account and working SSH access, with zero console interaction at any point.

The same "spin, run, use, discard" goal applies. The further motivation (stated directly by the project owner after Plan 2 shipped): once a Linux VM can be stood up unattended, it becomes something the project owner's AI assistant can actually operate — connect in over SSH, run the owner's dotfiles installer, and iterate on its UX. Setting up SSH keys and chezmoi for that follow-on use is explicitly **out of scope for this plan** — it happens after Plan 3 ships, as its own separate piece of work.

## Goals

- A single new menu action creates a VM and drives it, unattended, to a logged-in Ubuntu Desktop with a known local account and a working SSH server — no console interaction at any point, including GRUB's menu.
- Every setting that has a value (computer name, locale, timezone, disk size, credentials) is a parameter with a sensible default — nothing hardcoded — matching Plan 2's convention, so the action works identically from the interactive menu and from a scripted/AI-driven caller.
- The tool knows, for certain, when the install is actually done — a real signal, not a guess — and shows progress plainly while it waits.
- Reuses Plan 1's and Plan 2's building blocks (`Select-LabIsoPath`, `Set-LabVMBootProfile`, `New-LabSeedIso`, workspace helpers, the progress/orchestrator shape from `Start-LabWindowsVMProvisioning`) and issue #3's already-shipped SSH tooling (`Get-LabSshToolingInfo`, `Invoke-LabSshCommand`, `Add-LabSshKnownHost`, `Get-LabGuestAddressCandidates`) rather than duplicating them.

## Non-goals

- Any Linux distribution other than Ubuntu Desktop (decided earlier, before Plan 2 started).
- Domain join, telemetry customization, anything beyond what's needed to reach a working desktop + SSH session unattended.
- Copying SSH keys, dotfiles, or chezmoi files, or running the dotfiles installer — that is the next, separate piece of work, done manually (by the owner, or later by the AI assistant) using the existing, already-shipped file-transfer tooling.
- A generic N-drive media manager — exactly two DVD drives (installer + seed), same as Plan 2.
- Password-based SSH automation. OpenSSH's `InteractivePassword` path in this codebase deliberately leaves the password prompt attached to the operator's real console (`Invoke-LabSftpCommand`'s own code comment: "OpenSSH's own password prompt must reach the operator's real console unmodified ... a future reader should not 'fix' this branch to match the batch-mode one above"). An unattended retry loop has no operator at the console to answer that prompt, so this plan cannot and does not try to drive it.

## Anti-goals

- Anything that leaves GRUB's menu waiting silently for a keypress that will never come.
- Guessing "is it done" from a heartbeat or a quiet period, rather than a real, working SSH login — same reasoning as Plan 2's PowerShell Direct check.
- A password-only credential model that would force this plan into the forbidden `InteractivePassword` automation path above.

## Already proven (this session, live, on this host)

- **Ubuntu's installer (Subiquity) needs two separate things, not one.** A `cidata`-labelled NoCloud seed volume (`user-data` + `meta-data` at its root) is necessary but not sufficient — Subiquity also requires the literal `autoinstall` kernel boot parameter as a deliberate safety gate, confirmed in Canonical's own autoinstall documentation. Without it, Subiquity runs its normal interactive installer even with a valid seed attached. Both pieces are required together.
- **The GRUB boot menu can be patched in place, and this was proven by actually doing it against the real Ubuntu ISO on this host.** `grub.cfg` is a small plain-text file living inside an ISO9660/Joliet filesystem image, with real slack space inside its own sector (unlike Plan 2's problem, there is no fixed-size boot-catalog region to respect). The live test: copied the ISO, located `grub.cfg`'s sector, inserted ` autoinstall` into the relevant `linux` boot line, re-wrote the sector, remounted the patched copy, and read `grub.cfg` back — the edit was present and correct. This is a simpler, lower-risk mechanism than Plan 2's El Torito boot-catalog byte-swap: no boot catalog to parse, no equal-length constraint on the patch.
  - **New wrinkle Plan 2 didn't have:** because the file's content length actually changes (confirmed in this session: 543 → 553 bytes for the test edit), the directory-record length field for `grub.cfg` has to be patched too — in **both** the plain ISO9660 directory tree and the parallel Joliet tree, since the same file is listed in both. This was done live and confirmed correct in the same test; it is more surgery than Plan 2 needed (which only overwrote bytes in place, never changing a length), but it is proven working, not theoretical.
  - **Not yet proven:** nobody in this session has elevated Hyper-V access, so the patched ISO has never actually been booted end-to-end. The first live-test item for this plan is the same shape as Plan 2's: boot the patched ISO and confirm it reaches installation with zero console interaction.
- **Subiquity's `interactive-sections` is empty (fully silent) by default.** No extra autoinstall.yaml setting is needed to suppress interactive sections — this isn't a lever this plan has to pull.
- **`identity.password` requires a real crypt(3)/SHA-512-crypt hash (`$6$...`)**, which .NET has no native way to produce (no PowerShell/.NET BCL equivalent of `openssl passwd -6` or Python's `crypt` module was found). Canonical's own autoinstall documentation shows the accepted workaround: ship a throwaway placeholder hash that satisfies the schema, then set the real password from inside the install via `late-commands` using tools that already exist on the Ubuntu side (`curtin in-target -- chpasswd`). **Not yet live-tested** — this plan's second open risk (see "Decided" below for how it's handled).
- **Ubuntu Desktop does not ship `openssh-server` by default.** Reaching a working SSH server unattended requires `ssh.install-server: true` in autoinstall.yaml, which needs genuine package-archive access during the install — a new dependency Plan 2 never had (Plan 2's Windows install is fully offline-capable). Plan 2's own VM defaults already solve this for free: `Start-LabWindowsVMProvisioning` defaults new VMs to `-SwitchName 'Default Switch'`, Hyper-V's own NAT switch with built-in internet access, landed earlier in this session at the project owner's request. Plan 3 inherits that same default rather than inventing its own networking story.
- **The target ISO, confirmed present on this host:** `E:\ISO\ubuntu-26.04.1-desktop-amd64.iso` — current Ubuntu Desktop LTS. This is the ISO today's live `grub.cfg` test was performed against; "Already proven" above is only proven for this release's `grub.cfg` shape, not Ubuntu generally.
- **Not yet proven, flagged as an open risk rather than an assumption to build on blind:** whether a stock Ubuntu Desktop autoinstall brings up the Hyper-V KVP daemon (`hv_kvp_daemon` / `linux-cloud-tools`/`linux-azure` integration) without being told to. `Get-LabGuestAddressCandidates` (reused for the completion-poll's address discovery, same as Plan 2) reads the guest's IP through `Get-VMNetworkAdapter -IPAddresses`, which for a Linux guest depends on that service actually running and reporting. No guest has booted yet in this session — this needs confirming on the first live boot test, alongside the GRUB-patch boot test itself, and `autoinstall.yaml`'s package list may need an explicit KVP-related package if it turns out not to be present out of the box.
- **`New-LabSeedIso` (Plan 1) is already generic enough for this with zero changes.** It takes an arbitrary `-Files` hashtable and an arbitrary `-VolumeLabel`; nothing about it is Windows-specific. Building the NoCloud seed is `New-LabSeedIso -Files @{ 'user-data' = $userData; 'meta-data' = $metaData } -VolumeLabel 'cidata' -OutputPath ...` — the same function Plan 2 uses for `Autounattend.xml`, just with different volume label and file names.

## Decided, as decided

- **The new action creates the VM and provisions it in one continuous flow**, the same "create and provision" shape as Plan 2 — a new, separate menu action, not an extension of `N` or `M`. It reuses `New-LabVMCore` for VM creation and Plan 1's boot-profile/media/seed-ISO functions for preparation.
- **Two DVD drives, Linux-flavored equivalents of Plan 2's Task 3 functions**, not a reuse of Plan 2's own `Set-LabVMUnattendedInstallMedia`/`Complete-LabWindowsProvisioning`. Those two functions are already Windows-specific in their own parameter names (`-WindowsIsoPath`) and were built fresh for Plan 2 rather than generalized from Plan 1's single-drive `Set-LabVMInstallMedia` — this plan follows the same precedent and adds its own (e.g. `Set-LabVMUnattendedLinuxInstallMedia` / `Complete-LabLinuxProvisioning`) rather than touching already-shipped, reviewed Windows code to make it generic. Drive 1: the patched Ubuntu ISO, first in boot order. Drive 2: the `cidata` seed ISO — discovered by Subiquity scanning attached media, not part of the boot order.
- **Completion detection is a real signal: a working SSH login, over key-based auth, not a guess and not password auth.** As established in "Already proven" and "Non-goals" above, this codebase's `InteractivePassword` SSH path is deliberately interactive-only and cannot be driven by an unattended retry loop. The resolution: this plan generates a fresh, ephemeral SSH keypair per provisioning run (not the operator's own personal key — those stay out of the automated flow entirely, consistent with "we set up real SSH keys and chezmoi after this plan ships"), seeds the **public** half into the guest via autoinstall's `ssh.authorized-keys`, and polls for a working SSH session using that key and issue #3's existing `KeyAgent` auth mode (already shipped, already safe to automate — it's exactly the path `-ConfigureSsh`'s non-interactive mode already uses).
  - **Host-key trust during the completion poll (confirmed with the project owner):** every SSH-touching function in this codebase (`Invoke-LabSshCommand`, `Invoke-LabSftpCommand`, `Test-LabSshConnection`) hardcodes `StrictHostKeyChecking=yes`, and the only existing way to add a host key to `known_hosts` is `Add-LabSshKnownHost` — interactive by design, an operator reading a fingerprint off the guest console and typing `yes`. A freshly created VM's host key has never been trusted by anyone, so the completion poll's very first connection attempt would otherwise fail host-key verification. Resolution: the completion-poll's own SSH/SFTP calls — a new, narrowly-scoped call path, not a change to `Invoke-LabSshCommand`/`Invoke-LabSftpCommand` or their existing `StrictHostKeyChecking=yes` behavior — use trust-on-first-connect (`StrictHostKeyChecking=accept-new`) for this one ephemeral key against this one freshly created VM, during the narrow provisioning window only. Once provisioning succeeds, ordinary post-provisioning SSH use goes through the existing, unmodified `StrictHostKeyChecking=yes` functions, with the host key now already present in `known_hosts` (left to the builder: where this plan's first `accept-new` connection records that key, so the operator is never asked to separately trust it again through `Add-LabSshKnownHost`).
  - The account's actual login password (set via the placeholder-hash + `late-commands: chpasswd` workaround from "Already proven") stays in place too, for console/`sudo` use — it is not the mechanism this plan's own completion check or any follow-on automation relies on.
  - **The ephemeral private key is not deleted — it becomes the VM's permanent SSH identity, consistent with the "auto-save SSH connection settings on successful unattended install" decision from the original issue #2 brainstorming.** On the second (post-cleanup) successful login, this plan calls `Set-LabSshConnectionSettings` with the VM's address, the provisioned username, and this key's path, exactly the settings `Get-LabSshConnectionSettings`/the menu's existing SSH-dependent actions already expect. Two consequences this corrects from an earlier draft of this document: (1) the key must survive the pre-second-boot cleanup step, not be deleted by it — cleanup removes the installer/seed DVDs, the placeholder-hash autoinstall file, and the answer-file workspace, but not this key; (2) because `Set-LabSshConnectionSettings` persists only a path reference (`%LOCALAPPDATA%\LabVmManager\SshConnections\<VMId>.json`), the key itself cannot live in the per-VM provisioning workspace that gets deleted on cleanup — it needs its own stable home (e.g. alongside that settings file, as `...\SshConnections\<VMId>.key`), left to the builder to pin down exactly.
- **The completion note is delivered over that same SSH session**, after the first successful login — mirroring Plan 2's "the host delivers the note once PowerShell Direct connects," just over SSH/SFTP instead.
- **Progress while waiting:** blocks in the foreground with live progress, same as Plan 2 — no background-job model exists in this tool.
- **Every configurable value is a parameter with a default**, following Plan 2's exact convention:
  - `-ComputerName` (default `lab-agent-test-linux`, distinguishing it from Plan 2's Windows default)
  - `-Locale` (default `en_US.UTF-8`)
  - `-TimeZone` (default matching Plan 2's `Central America Standard Time`, translated to its IANA equivalent for autoinstall's schema)
  - `-VhdxSizeGB` (default `150`, matching Plan 2)
  - Username and password: typed interactively by default, overridable via parameters — same convention as Plan 2 and the existing file-transfer tooling.
- **Cleanup on success is a second boot cycle**, exactly mirroring Plan 2's reasoning: once the first SSH login succeeds (proving the install is genuinely done), the VM is shut down once more to eject/remove the seed DVD, eject the installer DVD, reset boot order to disk-first, and delete the host-side provisioning workspace — the placeholder-hash autoinstall file and the answer-file scratch copies, but **not** the ephemeral SSH private key, which per the note above has already moved to its stable, non-workspace home before this step runs. Then it starts again and the action waits for a second successful SSH login (using that same key) before declaring done, which also proves the VM boots cleanly standalone.
  - **On failure or timeout:** same as Plan 2 — the VM is left exactly as it is for inspection, nothing is auto-deleted, and the error output names the workspace path and states plainly that it holds sensitive material (the placeholder-hash file, the SSH private key if it hasn't yet been moved to its stable home).
- **VM hardware is not reinvented here either** — same `New-LabVMCore` path `N` and Plan 2 already use, with the same `-SwitchName 'Default Switch'` default Plan 2 already set (which, per "Already proven" above, is also what gives this plan the internet access `ssh.install-server: true` needs during install). If the caller overrides `-SwitchName ''` (no network), this plan's install will fail partway through package fetch — the action should fail loud with a clear message pointing at that, not a generic timeout, rather than silently assuming connectivity will be there.
- **Scripted/AI invocation gets its own top-level mode switch**, following the same `-CopyToVM`/`-ConfigureSsh`/Plan 2 pattern already established on `Lab-VM.ps1`.

## Linux ISO scope

**Ubuntu Desktop 26.04.x only** — matching `E:\ISO\ubuntu-26.04.1-desktop-amd64.iso`, the ISO today's live `grub.cfg` test used. Other distributions, Ubuntu Server, and other Ubuntu releases are explicitly out of scope: Subiquity's desktop-autoinstall support and `grub.cfg`'s exact on-disk shape are not guaranteed to match across releases, and this plan's binary surgery (directory-record length-field patching on top of the content edit) is specifically keyed to what was proven against this one ISO.

**The tool detects and refuses an out-of-scope ISO clearly, rather than letting it fail wherever it happens to fail** — the same fail-loud pattern Plan 2's "Windows version scope" already established. Ubuntu ISOs carry a plain-text `.disk/info` file at their root (e.g. `Ubuntu 26.04.1 LTS "..." - Release amd64`) readable the same way Plan 2 reads `sources\install.wim` metadata (mount, read, dismount in a `finally`) — the check happens before anything is built or attached.

## What's left to the builder

- Exact `autoinstall.yaml` structure: `identity`, `ssh` (`install-server: true`, `authorized-keys`), `late-commands` for the password workaround, `storage` layout (a single-disk UEFI/GPT layout, matching Plan 2's Windows partitioning intent), and anything else needed to reach a desktop with zero prompts.
- The exact placeholder password hash to ship in `identity.password`, and the exact `late-commands` invocation that replaces it — sourced from Canonical's own documented example rather than invented, with careful attention to shell-quoting the real password safely through the YAML string → `curtin in-target` → `chpasswd` chain (this is a genuine injection-shaped risk, same category as Plan 2's XML-escaping of the password into `Autounattend.xml`).
- The mechanics of the in-place `grub.cfg` patch as a reusable function (`New-LabPatchedBootableLinuxIso` or similar): locating the sector, inserting the kernel parameter, updating both the ISO9660 and Joliet directory-record length fields, and refusing cleanly (not corrupting the sector) if a future Ubuntu ISO's `grub.cfg` sector doesn't have enough slack space for the edit.
- The ephemeral SSH keypair's generation mechanism (host-side, before the VM is created, e.g. via `ssh-keygen.exe` already required by `Get-LabSshToolingInfo`'s tooling check) and its exact stable storage path once moved out of the provisioning workspace (e.g. `%LOCALAPPDATA%\LabVmManager\SshConnections\<VMId>.key`, sibling to the existing connection-settings JSON) — see the "Decided" section above for why it is kept, not deleted.
- The SSH completion-check polling loop's shape: retry interval, overall timeout, and progress-display wording — a Linux-flavored sibling of Plan 2's `Wait-LabPSDirectSession`/`Write-LabProvisioningNote`, not a shared abstraction forced onto both OSes (Plan 2's own design doc already anticipated this: "Plan 3 will reuse the already-shipped SSH tooling for its own completion check ... likely parallel-but-separate code, not shared code").
- Exact `autoinstall.yaml` network/proxy handling if the host sits behind one, and what error the action surfaces if `ssh.install-server: true` fails to fetch during install (distinct from a general install failure, if detectable).
