# Hyper-V acceptance checklist

**Status: partially exercised live** — the "Before mutation" checks and disposable-baseline checkpoint creation have been run against real `LAB-*` VMs; restore, rename, deletion, export, concurrency and shutdown-failure sections below have not yet been walked end-to-end. Use one disposable `LAB-*` VM with no valuable data. Do not use production, domain-controller, shared-disk, or customer VMs. Record host/guest OS versions and the Hyper-V module version alongside the audit log.

## Before mutation

- Run `Test-LabVM.ps1` in Windows PowerShell 5.1. It must parse the full manager and pass the helper checks.
- Run the manager without elevation: it must refuse VM operations with a useful message.
- Run `-ReadOnly`. Confirm only LAB-prefixed VMs appear, including lowercase `lab-` names. Non-LAB VMs must not be offered.
- Confirm selecting invalid numbers or letters does not start any VM action.
- Select one VM, inspect details and list checkpoints. Try a changing operation in read-only mode: it must be blocked.
- Confirm R refreshes immediately, B returns to the VM list, and Q exits.
- Confirm the host audit file exists outside the guest.

## Create VM

- Run `-ReadOnly`. Confirm the VM list prompt does not offer `N`, including when the inventory is empty, and that typing `N` is not treated as a create request.
- Run normally with no `LAB-*` VMs present (or a filtered view). Confirm the empty-inventory message mentions `N` and that choosing `N` starts the create workflow.
- Start a create, enter a name that does not start with `LAB-`: it must be rejected with a re-prompt, not accepted.
- Start a create, enter a name matching an existing VM (case-insensitive): it must be rejected with a re-prompt.
- Start a create, enter names containing `\`, `/`, `:`, `*` or `?` (e.g. `LAB-a\..\b`): each must be rejected with a re-prompt.
- At the VM storage root and VHDX storage root prompts, enter a relative path (e.g. `VMs`), a UNC path (e.g. `\\server\share`) and, if available, a mapped network drive: each must be rejected with a re-prompt.
- Cancel a create at any prompt, then confirm the VM list redraws normally and selecting an existing VM and running an operation (e.g. option 1) still works in the same session.
- Enter an out-of-range or non-numeric vCPU count (0, negative, text, or above the host's logical processor count): it must be rejected with a re-prompt.
- Enter an invalid memory spec: for dynamic memory, minimum greater than startup, or startup greater than maximum, or a value not a multiple of 2MB; for static memory, a zero/negative startup value. Each must be rejected with a re-prompt.
- Reach the preview screen and cancel at the `CREATE <name>` confirmation (type anything else, or press Enter): verify no VM, folder or VHDX was created, and that the audit log has no `create-vm` `STARTED` entry for this attempt.
- Complete a create with valid inputs: verify the new VM appears in the next inventory refresh, is Generation 2, has Standard checkpoint policy with automatic checkpoints disabled, has the requested vCPU/memory, and its VHDX is attached. Verify `create-vm` `STARTED`/`COMPLETED` audit entries exist with the new VM's ID. Also inspect the on-disk folder structure under the VM storage path (`<storage root>\<name>\...`) in File Explorer or Hyper-V Manager: confirm it matches expectations and is not unexpectedly double-nested (e.g. an extra `<name>\<name>\Virtual Machines\...` layer created by Hyper-V under the already name-qualified path).
- Repeat creation using the same name and storage root as a prior successful create: it must be rejected before any Hyper-V call because the dedicated VM/VHDX destination already exists.
- Choose "Disconnected" for the switch: verify the new VM's network adapter has no switch attached.

## Edit VM settings

- Select a disposable VM while it is Running or Saved; choose option 11: it must refuse with a message requiring Off, and make no change.
- Shut down normally, then choose option 11. Verify every prompt shows the VM's current value (name, notes, vCPU count, dynamic/static memory, min/startup/max bytes, current switch or Disconnected) and that pressing Enter on every prompt keeps that field unchanged.
- Repeat with every field left blank through to the diff screen: it must report no changes and return without a confirmation prompt or any audit `COMPLETED` entry. Do this on a static-memory VM too (one whose stored minimum/maximum differ from its startup memory, e.g. Hyper-V's 512MB/1TB defaults): it must still report no changes.
- Change only the casing of the name (e.g. `LAB-Test` to `LAB-test`): it must be shown as a Name change and require the `EDIT <name>` confirmation, not be treated as no change.
- Enter a new name that does not start with `LAB-`, or that matches another existing VM's name (case-insensitive): it must be rejected with a re-prompt, not accepted.
- Change only the vCPU count to a valid new value, confirm with the exact `EDIT <name>` phrase, and verify the diff screen listed only that field. After completion, confirm the new vCPU count in Hyper-V Manager or option 1, and that notes/memory/switch are unchanged.
- Change the memory spec to an invalid combination (e.g. minimum greater than startup under dynamic memory): it must be rejected with a re-prompt, not applied.
- Change the network switch selection to a different existing switch, then to "Disconnected": verify the adapter's switch updates to match each choice.
- Cancel at the final `EDIT <name>` confirmation after making a change: verify no setting was altered and no `COMPLETED` audit entry was written for this attempt.
- If the VM has more than one network adapter, confirm the tool states which adapter it manages and leaves the others untouched.

## Disposable baseline

- Shut down the guest normally. Select option 10 and cancel the confirmation: policy must not change.
- Confirm option 10; verify Standard policy and automatic checkpoints disabled.
- Create checkpoint `acceptance-baseline`. Verify its full ID appears in inventory.
- Try the same name again: it must be rejected without replacing anything.
- Start the VM. Attempt checkpoint creation while Running: it must refuse.
- Save a harmless marker file inside the guest, and a separate marker outside the guest on the host.
- Request graceful shutdown. Verify Off; verify no hard-power-off command appears in the log.

## Restore cancellation and safety

- Choose restore, select `acceptance-baseline`, cancel at the safety prompt. No checkpoint or restore should occur.
- Repeat; accept safety, but enter the wrong typed confirmation. No checkpoint or restore should occur.
- Repeat with safety enabled and the exact confirmation. Record the newly created safety checkpoint ID.
- After restore, verify no automatic start/resume was issued. Start manually. The guest marker should be absent; the host marker must still exist.
- Shut down. Restore the safety checkpoint and start manually. The guest marker should return.
- To test a failed safety precondition safely, change checkpoint policy away from Standard while Off. Request restore with safety enabled. It must stop before restore because safety checkpoint creation is disallowed. Restore Standard policy afterward.

## Rename and single deletion

- Create two disposable checkpoints, noting parent/child relationships and all IDs.
- Rename one. Its ID should be unchanged, with only the name changed.
- Cancel deletion: inventory should be unchanged.
- Delete only the selected disposable checkpoint. The other checkpoint must remain.
- Confirm no script operation directly deletes disk files. Let Hyper-V finish storage work.
- Test a baseline-looking name such as `10-acceptance-only`; deletion must require `DELETE BASELINE ...`.

## Scope and concurrency

- Start two manager sessions. Keep a changing operation's confirmation prompt open in the first. The second must refuse an operation on the same VM because of the per-VM mutex.
- Cancel the first; the second should then work. A different LAB VM should not share that lock.
- On an otherwise idle disposable VM, select it in the manager, then rename it out of LAB scope using Hyper-V Manager. The next manager refresh/operation must reject it, not select another VM with a similar name. Rename it back afterward.
- Do not use this rename test during a live checkpoint/export action; the mutex does not control Hyper-V Manager.

## Shutdown failure

- Use a disposable guest that cannot accept graceful shutdown, such as one without enabled shutdown integration. Request normal shutdown. The script must stop with an error or timeout, never hard-power-off automatically.
- Confirm timeout output says the request may still finish and requires inspection before retrying.
- Emergency power-off is optional to test and destructive. Test only on a fully disposable guest after saving all relevant work; exact confirmation is required. Recover the guest before taking another clean baseline.

## Export

- Select an existing local export root. Cancel: no export folder should be created.
- Complete an export of the Off VM. Verify a unique export subfolder, VMCX configuration, virtual disks where applicable, and `COMPLETE` manifest.
- Repeat to the same root: the earlier export must not be overwritten.
- Preserve any failed export and confirm the manifest is INCOMPLETE or IN_PROGRESS, not trusted COMPLETE.
- Import a COPY using Hyper-V Manager's copy/new-unique-ID option into an isolated test location. Do not start both copies on a sensitive network with duplicate guest identity. Validate actual boot/recovery before trusting the export as a backup.
- Delete test VMs/exports manually only after confirming they are disposable and no longer needed, or use option 12 (see "Delete VM" below) for the VM itself; either way the script never purges virtual disk files on its own.

## Delete VM

- Select a disposable VM, note its removal preview (name, GUID, path, disk paths, checkpoint count), and cancel at the "Export this VM before deletion?" prompt by choosing `C`: verify the VM, its checkpoints and its disk files are all untouched, and that no `delete-vm` audit entry was written.
- Repeat, this time answering `N` to skip the export, then cancel at the final `DELETE VM <name> <ID prefix>` confirmation (type anything else, or press Enter): verify nothing changed and no removal manifest was written.
- Create a non-Standard (recovery/backup) checkpoint on a disposable VM — for example via a backup application, or `Checkpoint-VM -SnapshotType ... ` outside this tool — and attempt option 12: verify it refuses immediately with a message about unresolved recovery/backup checkpoints, before any export/confirmation prompt, and that the VM is unaffected. Remove that checkpoint afterward.
- On a VM with only Standard checkpoints (or none), choose option 12, answer `Y` to export, and complete the export normally: verify the export reaches `COMPLETE`, then the removal preview is re-shown, and the final `DELETE VM <name> <ID prefix>` confirmation is required before anything is removed.
- Type the exact `DELETE VM <name> <ID prefix>` confirmation: verify the VM disappears from Hyper-V Manager/inventory, a `<VM ID>-removal-manifest.json` file exists next to the host audit log with `ExportPerformed: true` and a populated `RemovedUtc`, and the console reports the retained disk paths. Confirm those `.vhdx`/`.avhdx` files are still present on disk at the reported paths.
- After that successful delete, open the host audit log: the final record for this attempt must be `delete-vm-menu` with status `COMPLETED` (carrying the deleted VM's ID/name), not `FAILED_OR_UNCONFIRMED`, and the console must not print an "Operation failed or completion is unconfirmed" warning.
- Repeat on a different disposable VM, this time answering `N` to skip the export, and complete the deletion: verify the removal manifest shows `ExportPerformed: false`, disk files are still retained on disk, and the VM is gone from inventory.
- Start a manager session, select a disposable VM while it is Running or Saved, and choose option 12: verify it refuses with a message requiring Off, and makes no change.
- Confirm no script operation directly deletes `.vhdx`/`.avhdx` files during any of the above; only `Remove-VM` (through the Hyper-V API) is used, never manual file deletion.

## PowerShell Direct connection test

- Select a disposable Windows guest while it is Running, with valid local/domain Windows credentials known. Choose option `T` and enter the correct credentials: verify it reports success and prints the guest's OS version string, and that the session is closed afterward (no leftover `Get-PSSession` entries on the host).
- Repeat with a deliberately wrong password: verify it reports a clear failure message (e.g. an authentication error), never a raw .NET stack trace, and that no session is left open.
- Shut the guest down (`Off`), then choose option `T`: it still prompts for credentials first (per the function's fixed order), but then refuses before opening any PowerShell Direct session, reporting the `Assert-LabVMRunning` message naming the VM's actual state. No session is ever attempted.
- Confirm `-ReadOnly` mode still offers option `T` and that it behaves identically to normal mode (no mutation is possible through this option).

## SSH connection configuration (menu and CLI)

- **Menu, with a suggested address.** Select a disposable Running Linux guest with at least one non-link-local IPv4/IPv6 address. Choose option `C`. Verify its own current IP address(es) are listed as numbered suggestions, but nothing is pre-filled or auto-selected at the hostname/address prompt. Type the listed number for one of the suggestions (or type the address itself) to confirm both work; leave the port prompt blank and confirm the preview shows `Port: 22`; supply a username; leave the identity-file prompt blank (password auth). Review the preview (VM name/ID, host/address, port, username, `AuthMode: Password (prompted at connection time)`), answer the `[Y/n/cancel]` confirmation with Enter (default Yes), and confirm the console reports "SSH connection settings saved." If this host has never connected to the guest, trust its key first with option `K` (see "Trusting a new guest's host key (`K`)" below). Then choose option `13` (or `14`) and copy a small file to/from the guest: confirm the transfer succeeds over SSH (no PowerShell Direct credential prompt appears) and that option `T` on this VM now reports success via `Test-LabSshConnection`'s own "Connection succeeded" message, not the PowerShell Direct connectivity test.
- **Menu, blank re-prompts.** Choose option `C` again on the same VM. At the hostname/address prompt, press Enter with nothing typed: verify it re-prompts ("Enter a hostname or address.") rather than silently defaulting to a suggested address. At the username prompt, press Enter with nothing typed: verify the same re-prompt behavior. At the final `[Y/n/cancel]` confirmation, answer `C` (or `N`): verify the console reports the settings were not changed, and that `Get-LabSshConnectionSettings` for this VM still reflects whatever was saved before this run (or nothing, if this is the first configuration attempt).
- **CLI, `-ConfigureSsh`.** Run `powershell.exe -NoProfile -File .\Lab-VM.ps1 -ConfigureSsh -VMName <that Linux VM> -SshHost <address> -SshUser <user> -SshIdentityFile <path to a working private key>`. Verify it never prompts for anything, reports "SSH connection settings saved for VM ...", and exits `0` (`$LASTEXITCODE`). Then, without reopening the menu, run `& .\Lab-VM.ps1 -CopyToVM -VMName <that VM> -SourcePath <file> -DestinationPath <path> -NonInteractive`: verify it completes over SSH/SFTP (no Windows credential is requested, and none was supplied) -- confirming `-ConfigureSsh` alone is enough to switch that VM's adapter to SFTP for a later, separate invocation. Then run `-ConfigureSsh` again with only `-VMName` and `-SshHost` (omitting `-SshUser`): verify it exits `1` with a message naming `-SshUser` as missing, and that the previously saved settings are unchanged. Finally, run `-ConfigureSsh` together with `-CopyToVM` in the same invocation: verify it exits `1` with the "Supply only one of -ConfigureSsh, -CopyToVM, or -CopyFromVM" message, before any host/VM check runs.
- **Invalid values are refused.** Run `-ConfigureSsh` with `-SshUser '-oProxyCommand=calc'`, then with `-SshHost '-oProxyCommand=calc'`, then with `-SshPort 70000`: each must exit `1` with a message naming the parameter, no `calc` (or any other process) may start, and the saved settings must be unchanged. In menu option `C`, enter a hostname or username starting with `-` (or containing a space): it must be refused with a re-prompt.
- **Corrupt settings file.** Overwrite the VM's `%LOCALAPPDATA%\LabVmManager\SshConnections\<VMId>.json` with `{ not json`. Option `T`, option `13`/`14` and parameter-mode `-CopyToVM` must each fail with an error naming that file -- never fall back to PowerShell Direct (no Windows credential prompt). Option `C` must warn about the file and, once you save, replace it. Then delete the file: the VM must use PowerShell Direct again (option `T` asks for Windows credentials), which is the documented way back from SFTP.
- **Regression: Windows VM is unaffected.** Select a disposable Windows guest that has never had option `C` or `-ConfigureSsh` used against it (confirm with `Get-LabSshConnectionSettings` returning `$null` for its ID, e.g. via `Test-LabVM.ps1`'s harness or by checking `%LOCALAPPDATA%\LabVmManager\SshConnections\<VMId>.json` does not exist). Choose option `T`: verify it still prompts for guest Windows credentials and runs the PowerShell Direct connectivity test exactly as before this task, not `Test-LabSshConnection`. Choose option `13` or `14` and copy a file: verify it still uses PowerShell Direct (credential prompt, `New-PSSession -VMId`), with no change in behavior from before this task. This is the explicit check that adding SSH configuration does not change any existing Windows-guest behavior.

## SSH connection test (Linux guest)

- Against a reachable Linux guest with an SSH server running (or socket-activated) and a saved connection configured with a valid identity file: run `Test-LabSshConnection`. Verify it succeeds noninteractively (`KeyAgent` mode) -- no prompt of any kind appears -- reports success on the console, and that the temporary one-line batch file it creates is gone afterward (check the temp folder during and after the run).
- **Before trust.** Against a guest this host has never connected to (no entry for it in `~/.ssh/known_hosts`), in either auth mode: run option `T`. Verify it fails promptly with no prompt of any kind -- `StrictHostKeyChecking=yes` never asks about host keys -- and in `KeyAgent` mode the warning includes OpenSSH's own "Host key verification failed." text, followed by the hint pointing at options `K` and `U`. Confirm `known_hosts` was not changed.
- Against the same guest, after trusting its key with option `K` (below), with no identity file saved (password auth): run `Test-LabSshConnection` (option `T`). Verify no host-key prompt appears (the key is already trusted), then the real OpenSSH password prompt appears on the actual console -- confirm neither the prompt text nor the typed password is captured or echoed anywhere in the manager's own `Write-Host`/`Write-Warning` output or the audit log. After entering the password, verify "Connection succeeded (InteractivePassword)" is reported, not "Connection test failed: The property 'ExitCode' cannot be found".
- Against a VM with no SSH connection settings saved at all: run `Test-LabSshConnection`. Verify it reports the "not configured, use Configure SSH connection first" message immediately, with no connection attempt of any kind (no prompt, no delay, no temp batch file created).
- Against a guest with password login disabled and no authorized key installed yet for the configured user: run `Test-LabSshConnection` in `KeyAgent` mode (with an identity file that the guest does not yet trust). Verify it fails cleanly and promptly with an actionable message (e.g. a permission-denied/authentication error surfaced from `sftp.exe`'s output), not a hang and not a raw stack trace.
- Changed host key: with a guest already trusted once, change its host key (reinstall the OS, restore an older snapshot that predates the current key, or regenerate host keys in the guest), then run `Test-LabSshConnection` again. Verify the connection fails with OpenSSH's own host-key-mismatch message. Choose option `K`: verify that even after the `TRUST HOST KEY <host>` confirmation, OpenSSH refuses the changed key (it never offers to replace it). Then choose option `U`: verify it previews the exact `host:port` entry about to be cleared, requires the exact `UPDATE KNOWN HOST <host>` confirmation (typing anything else cancels with no change to `known_hosts`), and only then runs `ssh-keygen.exe -R`. Run option `T` afterward: verify it still fails (clearing trusts nothing). Then use option `K` to trust the new key (below) and run `T` again: verify the connection succeeds.
- **Real password prompt during an actual payload transfer (not just `Test-LabSshConnection`).** `sftp`'s `-b` (batch-file) option silently passes `-oBatchMode yes` to its `ssh` child (confirmed by reading the bundled `sftp.exe` 9.5.6.4 binary and upstream `sftp.c`; the man page omits it), which would suppress password prompting for every payload operation. The manager therefore passes `-o BatchMode=no` before `-b` in password mode. This step is the live confirmation of that fix. Against a guest with no identity file saved (password auth, `InteractivePassword` mode) and an already-trusted host key, run an actual file copy -- menu option `13`/`14` or `-CopyToVM`/`-CopyFromVM` -- not merely `Test-LabSshConnection`. Verify the real OpenSSH password prompt appears on the live console for this payload transfer itself, that the transfer completes once the password is accepted, and that this holds for both a single-file upload and a single-file download. If no prompt appears and the transfer fails outright with exit `255`, the `BatchMode=no` override is not taking effect on this OpenSSH build: record that as a limitation in the README rather than assuming it away.

## Trusting a new guest's host key (`K`)

Use a disposable Running Linux guest with saved SSH settings that this host has never connected to (no `known_hosts` entry; check with `ssh-keygen -F <host>` or `ssh-keygen -F "[<host>]:<port>"` for a non-default port). Before starting, read the guest's fingerprint on its own console: `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.

- **Cancel at the manager's confirmation.** Choose `K`, read the explanation (it names the guest-console fingerprint command and says a changed key needs `U` first), and type anything other than the exact `TRUST HOST KEY <host>` phrase. Verify the console reports the cancellation, no `ssh` process starts, no OpenSSH prompt appears, and `known_hosts` is unchanged.
- **Answer `no` to OpenSSH.** Choose `K` again and type the exact `TRUST HOST KEY <host>` phrase. Verify that OpenSSH's own "The authenticity of host ... can't be established" prompt, with the key's `SHA256:` fingerprint, appears directly on the console, and that the manager prints nothing in between. Answer `no`. Verify the manager reports a non-zero ssh exit code, and `known_hosts` is unchanged.
- **Answer `yes` to OpenSSH.** Repeat, compare the fingerprint with the guest console's, and answer `yes`. Verify `ssh-keygen -F <host>` now finds the entry. In password mode, verify OpenSSH then asks for the password on the console; after entering it, the manager reports the key as trusted. Neither the fingerprint prompt, your answer nor the password may appear in the manager's own output or the audit log. Then choose `T`: it must succeed.
- **Already trusted.** Choose `K` once more: after the confirmation, OpenSSH must connect without any host-key prompt.
- **Only `K` asks.** After clearing the entry again with `U`, run `T`, menu `13` and parameter-mode `-CopyToVM`: none of them may show a host-key prompt; each fails with "Host key verification failed". Only `K` uses `StrictHostKeyChecking=ask`.
- **Read-only.** Start the manager with `-ReadOnly`: verify `K` and `U` are listed and behave the same (they change only the operator's own `known_hosts`, not the VM).
- **Not configured / not Running.** On a VM with no saved SSH settings, `K` and `U` report "SSH connection is not configured" and start nothing. On an Off VM with saved settings, `K` refuses with the `Assert-LabVMRunning` message before any confirmation prompt.

## Linux transfer engine

Run these against a disposable Running Linux guest once a caller is wired to `Copy-LabTransferItemSftp` (Task 5), in `KeyAgent` mode unless a step says otherwise. Use absolute paths on both sides. After every step, check that no `*.labxfer-*.tmp` item is left next to the destination on either side, except where a step expects one.

- **Round trip with `-VerifyHash`.** Copy a file of a few MB of random data from the host to the guest with `-VerifyHash`. Then copy it back to a new host path, again with `-VerifyHash`. Both runs must report `Completed = 1` with the correct `BytesTransferred`. `sha256sum` on the guest and `Get-FileHash -Algorithm SHA256` on both host copies must all match.
- **Single-file collision.** Copy a file onto an existing guest file. With `Error`, the result is `Failed = 1`, and the guest file's content and mtime are unchanged. With `Skip`, the result is `Skipped = 1`, also unchanged. With `Overwrite`, the result is `Completed = 1`, and the guest file now matches the source. In the `Error` and `Skip` cases, no temporary file appears at any point. Repeat in the from-VM direction.
- **Verify before finalize.** Run an `Overwrite` upload of a large file. While it is copying, watch the destination directory with `ls -la` on the guest console. The original file must stay in place, with its content unchanged, until the `.labxfer-*.tmp` copy is complete. It must then be replaced in one step.
- **Fresh directory.** Build a host directory containing a nested subdirectory, an empty subdirectory and a dotfile (for example `.bashrc`). Copy it recursively to a guest path that does not exist yet. On the guest, the whole tree appears at once, including the empty subdirectory and the dotfile, and no temporary tree is left behind. Repeat from the VM to a new host path.
- **Existing directory destination.** Copy a directory recursively onto an existing guest directory, under each `-OnConflict` value. Every run must fail with the "merging into an existing directory on the Linux/SFTP adapter is not supported in this version" message. Nothing inside the existing directory may change.
- **Nested symlink in a guest-side tree (the unverified item).** On the guest, create a symlink inside a source directory, for example `ln -s /etc/hostname tree/link` and `ln -s .. tree/up`. Copy `tree` recursively from the VM. Record what `get -r` actually did: followed the link, skipped it, or failed the copy. Also record whether the engine then refused the downloaded tree because it contained a reparse point. Then update the code comment at the `put -r`/`get -r` call in `Copy-LabTransferItemSftp`, the plan's Task 4 decision, and the README's limitation note to match what you observed. Do the same for an upload: put a junction inside a host-side tree. The upload must be refused with a "reparse point" message, and nothing may be copied.
- **Top-level symlinks.** On the guest, create a symlink to a directory and a symlink to a file. Use each one as the destination of an upload and as the source of a download. Every case must fail with a "symbolic link" message and nothing copied. This checks the `KeyAgent` parent-listing probe against the real `ls -la` output format, including any `-> target` suffix.
- **Missing parent directories.** Upload a file to `/tmp/lab-new/a/b/file.txt`, where `/tmp/lab-new` does not exist yet. First run a dry run: it must report "would copy … (creating 3 missing parent directories)" and create nothing. Then run the real transfer: it must complete and create `lab-new/a/b`. Repeat as a recursive directory upload, and from the VM to a new host path such as `C:\lab-dl\new\x\file.txt`. Then make an upload fail after the parents are created, for example `-VerifyHash` on a guest without `sha256sum`, into `/tmp/lab-empty/n1/n2/file.txt`, where `/tmp/lab-empty` is an existing empty directory. Afterwards, `n1` must be gone and `/tmp/lab-empty` must still exist. Run this in both auth modes. In `InteractivePassword` mode, creating the parents must not add a password prompt beyond the counts below.
- **Listing format (`KeyAgent`).** Run `sftp` interactively and capture `ls -la` of a guest directory. Check that every line, including `.` and `..`, has the shape the engine expects: mode, links, owner, group, size, month, day, time or year, name. If any line differs, an upload into that directory must fail with a "not recognized" message, never proceed. Also try a destination that is a device node (for example `/dev/null`, as a `Skip` upload). It must fail without writing anything.
- **Password mode.** With no identity file saved, run one single-file upload with `-VerifyHash`. Count the password prompts: there should be four (upfront check, upload, size/SHA-256 check, finalize). The result must match the `KeyAgent` result. Then run a single-file download (three prompts) and a fresh directory (two prompts). Make sure no prompt text or password appears in the manager's own output or in the audit log.
- **Guest without `sha256sum`, or an `sftp`-only account.** Run a `-VerifyHash` upload. It must fail with the "sha256sum is not available" message, or with the "POSIX-compatible login shell" message, and the destination must be untouched.
- **Failed recursive upload.** Make a recursive upload fail partway, for example by filling a small guest filesystem or by making a subdirectory unwritable after the copy starts. The real destination must not be created. The error must name the leftover `*.labxfer-*.tmp` directory, which you then remove by hand.
- **Connection loss.** Power off the guest during a large single-file upload. The transfer must stop with the "SSH connection failed during the transfer" error. The real destination must be untouched. A `*.labxfer-*.tmp` file may remain on the guest.
- **Private files (`-PermissionProfile PrivateFiles`), single file.** On the guest console, create `~/.ssh/` with an unrelated sibling file in it (for example `~/.ssh/config`) and note its mode with `ls -la ~/.ssh`. Generate a synthetic, throwaway private key on the host (never a real one) and upload that file on its own, not as part of a directory, to `~/.ssh/id_lab_test` with `PrivateFiles`. The result must be `Completed = 1`. `ls -la ~/.ssh` on the guest console must show `-rw-------` (`600`) for `id_lab_test`, owned by the SSH login account, and the sibling's mode must be unchanged. Repeat as an `Overwrite` onto an existing file whose mode is `644`: it must end up `600`. Run this in both auth modes.
- **Private files, directory.** Upload a small host directory (one nested subdirectory, two files) to a new guest path with `-Recurse` and `PrivateFiles`. On the guest console, `ls -la` of the parent must show the new root as `drwx------` (`700`). Then `ls -la` inside it and record the actual modes of a file and of the subdirectory. They are not guaranteed to be anything in particular: they come from the guest's SFTP server and the account's umask (`umask` on the guest console shows it). Record what you saw next to the limitation note in the README ("Private files on the Linux/SFTP adapter"), so that note matches real behavior. An unrelated sibling of the new root in the same parent must keep its mode.
- **Private files, failed `chmod`.** Make the final `chmod` fail after a successful copy. ## Transfer engine

Run these against a disposable Running Windows guest once a caller (menu option or parameter mode) is wired to `Copy-LabTransferItem`. Use absolute drive-letter paths on both sides. After every step, confirm no `*.labxfer-*.tmp` file or directory is left next to the destination on either side.

- Large file round trip: create a multi-hundred-MB file on the host (e.g. `fsutil file createnew` and then write random data into it, so it is not all zeros). Copy it to the VM with hash verification on, then copy it back from the VM to a new host path with hash verification on. Both runs must report `Completed = 1` and the correct `BytesTransferred`. `Get-FileHash -Algorithm SHA256` of the original and the round-tripped copy must match. Watch the host `powershell.exe` working set during the copy: it should stay flat, not grow by the file size.
- Single-file conflict: copy a file to a destination path that already exists as a file. With `Error`, the result must be `Failed = 1`, and the existing file must stay unchanged, with its modified time and hash the same as before. With `Skip`, the result must be `Skipped = 1`, again with the file unchanged. With `Overwrite`, the result must be `Completed = 1` and the destination must now hash the same as the source. In the `Error` and `Skip` cases, no temporary file should ever appear, because no copy is attempted.
- Type mismatch: copy a single file to a path that exists as a directory, and copy a directory with recurse to a path that exists as a file. Both must fail under every `OnConflict` value, including `Overwrite`, and nothing at the destination should change.
- Nested directory conflict: build a source tree with at least two levels of subdirectories. Pre-create the destination root containing the same subdirectory path and exactly one colliding file deep inside it, and give that file different content. Run a recursive copy once under each of `Error`, `Skip` and `Overwrite`, re-creating the destination fixture before each run.
  - `Error`: every other file is copied, and the colliding file is reported as a failed item and left unchanged.
  - `Skip`: every other file is copied, and the colliding file is reported as skipped and left unchanged.
  - `Overwrite`: every file is copied, including the colliding one, which now matches the source.
  - Do all of this in both directions (to the VM and from the VM).
- Repeat-copy nesting: run the same recursive copy to the same destination twice in a row. The second run must not create `dest\<source name>\...` nesting. Under `Skip`, every file must be reported as skipped. Under `Error`, every file must be reported as failed. Under `Overwrite`, every file must be replaced in place.
- Reparse points: inside the source directory, create a junction (`cmd /c mklink /J loop <source dir>`) and, if possible, a file symlink. Run a recursive copy. Each link must appear in the summary as a failed item with a "reparse point" message. The other files must still be copied. The destination must not contain the link, its target's contents, or a runaway nested `loop\loop\...` tree. Also pass a junction directly as the source: it must fail with nothing copied.
- Dry run: repeat the nested-conflict case with dry run enabled. The summary must show what would happen, but nothing at the destination may change, and no temporary item may be created on either side.
- Connection loss: start a large recursive copy, then turn the guest off or restart it mid-copy. The operation must stop with a connection error that states the counts reached before the failure. Afterwards, inspect the destination: only fully verified files may be at their real names. Any leftover `*.labxfer-*.tmp` item may remain on the guest, because cleanup cannot run over a lost connection, and can be deleted by hand.
- Private-file permission profile: create a synthetic private file (e.g. a throwaway "SSH key") inside a destination directory that already contains an unrelated pre-existing sibling file. Via **parameter mode**, run `-CopyToVM ... -PermissionProfile PrivateFiles` into that directory, then `-CopyFromVM ... -PermissionProfile PrivateFiles` back out to a second such directory on the host. Repeat both directions via the **menu** (options `13`/`14`), answering `Y` to the "Private files" prompt. For every run: `Completed = 1`; on the receiving side, `icacls`/`Get-Acl` on the copied file shows only the receiving account (the signed-in host user for a host destination, or the credential's guest account for a guest destination) with no inherited entries; and `icacls`/`Get-Acl` on the pre-existing sibling file is unchanged from before the run. Also run one recursive `PrivateFiles` copy into a brand-new destination directory and confirm the destination root directory itself is likewise restricted to the receiving account only; then repeat that recursive copy a second time (merging into the now-existing directory) and confirm the root directory's ACL is left as the first run set it (not reset or widened) and that any pre-existing, out-of-transfer sibling directory next to it is untouched.

## Parameter mode (file transfer)

- Lock: start the menu in one elevated window, select a Running disposable guest, and start a large option `13` copy. While it runs, in a second elevated Windows PowerShell 5.1 window run `& .\Lab-VM.ps1 -CopyToVM -VMName <that VM> -SourcePath <file> -DestinationPath <path> -Credential $cred`: it must exit `1` immediately with "Another copy of this script is operating on this VM. No transfer was started here." and copy nothing. Repeat with the roles reversed (a long parameter-mode copy running, then menu option `3` or `X` on the same VM in another window): the menu operation must be refused with its "Another copy of this script is operating on this VM" message.
- Audit: run one parameter-mode copy that succeeds, one with `-DryRun`, one under `-ReadOnly` without `-DryRun`, and one whose destination already exists under `-OnConflict Error`. The host audit log must contain one `file-transfer` record per run with status `COMPLETED`, `DRY_RUN`, `BLOCKED_READONLY` and `FAILED` respectively, each detail listing direction, paths, counts, conflict policy, permission profile and verify-hash, and never any credential material. The `-ReadOnly` run must not prompt for credentials.
- Credential: build `$cred = Get-Credential` in an elevated Windows PowerShell 5.1 window and run `& .\Lab-VM.ps1 -CopyToVM ... -NonInteractive -Credential $cred`: the transfer runs without prompting.
- Orphan parameters: run `powershell.exe -NoProfile -File .\Lab-VM.ps1 -VMName LAB-x -NonInteractive` (no `-CopyToVM`/`-CopyFromVM`): it must exit `1` with an error naming `-VMName, -NonInteractive`, without opening the menu or waiting for input.
